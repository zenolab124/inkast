# M2 入口必须从"无文本"出发

M2(字段精修)的进入点和 M1/M3 结构上**不同**——它必须从空文本/无文本态出发,因为 inkast 没有"不调 LLM 把散文拆字段"的能力。

## 背景

设计 M1/M2/M3 三模式渐进披露([three-modes-progressive-disclosure](./three-modes-progressive-disclosure.md))时,直觉是写完文本给用户三个并列分叉:[直接生图] [AI 扩充] [跳过文本进字段]。

但仔细推敲第三个分叉:**如果用户写了"一只橘色狐狸蹲在松树下",然后点"跳过文本进字段",该怎么处理那段文本?**

| 选项 | 问题 |
| --- | --- |
| a. 丢弃文本进 M2 | 用户辛苦写的没了——破坏性 |
| b. 文本保留 + 字段空白等用户填 | 散文和字段语义割裂,用户不知道哪个会被发送 |
| c. 弹"丢弃?"对话框 | 摩擦,且对话框抓不住"为什么必须丢弃"的根因 |

三种都不优雅。**根本原因**:M1/M3 的进入点是"已写文本",M2 的进入点结构上**不同**——它必须从"无文本"出发。

## 方案对比

| | 写文本后给 M2 入口 | **M2 入口只在初始态(选)** |
| --- | --- | --- |
| 直觉 | 三个模式视作并列分叉 | 承认 M2 是结构不同的路径 |
| 文本处理 | 必须丢弃 / 保留(都不好) | 用户主动选 M2 之前没文本——无文本可丢 |
| 老用户走 M2 | 写完文本再点 | **直接点底部"跳过文本"或 ⌘E** —— 更快 |
| 用户惊讶程度 | 点了之后文本被丢——可能投诉 | 入口语义直白:"跳过文本" = 不打算写文本 |

## 最终选择

M2 入口在**初始态(无文本时)**就给:

```
[ textarea (空) ]
[▶ 直接生图(禁用)] [✦ AI 扩充(禁用)]
── 或 ──
⊞ 跳过文本,直接编辑字段  ⌘E
↑ M2 入口在这里
```

**写了文本之后**,M2 入口**仍然在底部显示**(允许后悔),但点击会清空文本——这是预期行为,因为按钮文案明示了"跳过文本"。

实际场景里,真想用 M2 的用户大概率**不会先写文本**——他直接来字段。"写完文本切 M2"几乎不存在,设计这条路径没有 ROI。

## 副作用

- **必须有 ⌘E 全局快捷键** —— M2 入口在视觉上是次要的(底部小链接),老用户重度走 M2 时鼠标摩擦大。⌘E 解决这个问题,任何时候按都进 M2(从 M1/M3 锁定态切回 M2 也行)
- **从 M3 / M1 切回 M2 仍然走 skipText** —— 不论当前 state 怎样,`skipText()` 都会清空 prompt + 清空 input + 设置 lockMode="m2"。这是个干净的状态重置,不需要"M3 → M2"专门的迁移逻辑
